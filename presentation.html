Adaptive Chess Puzzle Advisor

An adaptive, weakness-targeted chess puzzle recommender built on a Thompson Sampling bandit,
Stockfish-verified puzzle mining, and Glicko-2 difficulty calibration.

Aleksandar RadevskiJuly – October 2026
Overview

What the system does

♟

Analyse

Pulls a player's Chess.com game history and estimates which of 23 tactical categories they're weakest in.

♞

Recommend, adaptively

A Thompson Sampling multi-armed bandit selects which category to practise next, updating in real time from every solve/fail.

♛

Mine & calibrate

Puzzles come from a 6M-row Lichess database plus puzzles mined directly from the player's own games; two offline models (Glicko-2, a trained classifier) extend the calibration further.

Pipeline 1

Player analysis — from games to a weakness profile

  • Every player move is evaluated before and after with Stockfish — a ≥50cp drop is logged as an error, with severity and now also a tactical category.
  • build_profile() converts error patterns into per-category weakness scores via hand-tuned thresholds (not learned — see slide 5).
  • A crude engine-free fallback exists for when Stockfish can't be located — more on that on slide 15.

Pipeline 3

The Thompson Sampling recommendation loop

Serving cascade order:

  1. User-mined puzzle, target category, unseen
  2. Any unseen mined puzzle (40% of the time)
  3. Lichess pool, target category, rating window
  4. Lichess pool, widened rating window
  5. Lichess pool, any category
  6. Last resort: allow a repeat, flagged explicitly

The mathematics

Thompson Sampling — why Beta(α, β)?

Each category is a Bernoulli process: every attempt is a solve (1) or fail (0) with unknown true probability pᵢ.

Beta is the conjugate prior for Bernoulli — the posterior after new evidence is exactly another Beta, in closed form:

if solved: arm.alpha += 1
else: arm.beta += 1
QuantityMeaning
α − 1effective solves seen (real + prior)
β − 1effective fails seen
α + βtotal confidence — bigger = narrower posterior
meanα / (α+β) — best point estimate
varianceαβ / [(α+β)²(α+β+1)] — shrinks with evidence
8 / 24
The mathematics, continued

Sampling — not averaging — is what makes exploration free

Worked example

"Fork" attempted 8×, solved 3× → α=4, β=6, mean=0.4. A sample might land at 0.28 (looks weaker) or 0.55 (looks fine) — both are legitimate draws. The randomness is the mechanism, not noise.

The one deliberate inversion

select_one() picks the lowest sampled θ, not the highest — θ measures proficiency here, and the goal is to practise weaknesses, not strengths.

Offline research component

Glicko-2 — beyond a single Elo number

SymbolNameMeaning
r / ratingRatingsame interpretation as Elo — higher is stronger / harder
RD / rdRating Deviationthe system's uncertainty — rating ± 2×RD ≈ 95% confidence interval
σ / volatilityVolatilityhow erratically true skill seems to move — real change vs normal noise

A bare Elo number can't tell "we're very sure" from "we just guessed." A new puzzle or player starts with high RD; it shrinks as real evidence accumulates.

Offline research component

Update mechanics & validation

  1. g(φⱼ) — discount by the opponent's own uncertainty
  2. E(μ,μⱼ,φⱼ) — expected outcome (logistic, like Elo)
  3. v — variance of the rating change
  4. Δ — actual vs expected outcome, scaled by v
  5. Solve for new σ′ via the Illinois root-finder
  6. Update φ′, μ′; convert back to (rating, RD)

Matches Glickman's own published example

1500 / RD200 / vol0.06, three games → 1464.06 / 151.52 / 0.05999, matched to tested tolerance.

Offline research component

Trained weakness classifier — build_profile_ml()

  • Drop-in alternative to the rule-based scorer — same signature, same output shape, only weakness_scores differs.
  • 30 input features: 7 coarse summary stats + 23 per-category observed error rates (now measurable thanks to the new MoveError.category field).
  • RandomForestRegressor predicts all 23 category weaknesses at once.
  • Trained on simulated players — only 4 real players have any mined-puzzle history, far too few for a statistically meaningful held-out-player split.
  • Synthetic data generated via a Dirichlet-multinomial process: true-weak categories get boosted concentration, so observed error counts are realistically noisy, not hand-tuned to look good.

Found by re-reading the live code — and fixed

Known limitations & discovered bugs

✓ Fixed — the real scorer now actually runs

analysis_start() used to look for Stockfish via shutil.which("stockfish"), which never checked the bundled binary — the app silently fell back to the crude heuristic scorer almost every time. Now calls find_stockfish() instead, the same resolver puzzle mining already used. build_profile() is the default path on every successful analysis.

✓ Fixed — all three weakness-scoring paths now wired together

Rule-based build_profile() is the default (per the fix above). The trained ML classifier build_profile_ml() is now reachable too, via a new WEAKNESS_MODEL=ml opt-in flag — deliberately not the default, since it's only validated on simulated players so far. Heuristic remains the last-resort fallback.

✓ Found & fixed live — a second bug the first fix exposed

Fixing the scorer meant Stockfish ran against real games for the first time. That immediately surfaced multipv=1 making engine.analyse() return a list, not a dict — crashing every move analysis. Caught in a live smoke test, fixed by dropping the unnecessary kwarg. Zero test coverage before this, since the unit tests are deliberately engine-free.

Still open: stale documentation & two difficulty-tier schemes

README and eval CLI docstrings quote outdated tuning constants; the Lichess pool and mined puzzles use two different tier boundaries. Cosmetic, not yet cleaned up — the honest remaining gap on this list.

Prepared answers

Anticipated questions — cheat sheet

If asked…Short answer
Is this reinforcement learning?Yes — a Bayesian multi-armed bandit (Thompson Sampling). Not deep RL: no neural policy network, no PPO/DQN.
How do you know the bandit actually works?Unit-tested directly: priors seed correctly, update() moves α/β the right way, select_one() statistically favours the weaker arm under a seeded RNG.
Where does puzzle quality assurance come from?Two independent layers: the 4-gate mining pipeline rejects bad extractions before saving; a separate 5-dimension evaluator re-scores whatever is kept.
What's the single biggest gap right now?Data volume, not methodology — only 4 real players so far. The Stockfish-detection bug that used to compound this (slide 15) is fixed.
Why Thompson Sampling, not UCB or epsilon-greedy?No separate tunable exploration parameter — posterior width does the exploring automatically, and it matches UCB-style performance for Bernoulli rewards.
What would you do with another month?Collect more real data, run a real A/B of build_profile_ml() vs the rule-based scorer, wire the Glicko-2 fitter into serving, clean up stale docs.
